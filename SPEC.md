# Спецификация «Marital Property v2»

Статус: **черновик 2.0.0-alpha** (02.09.2026). Всё, что помечено «требует подтверждения», должно быть проверено практикующим юристом до перевода в стабильную версию.

Спецификация описывает три вещи:

1. **Документ дела** — JSON, схема в `schema/marital-property.v2.schema.json`. Один и тот же документ хранится в файле `.divorce` приложения LawMatic Divorce и в `context_json.marital_property` дела Legalic.
2. **Движок расчётов** — набор чистых функций над документом (раздел 4). Реализуется на TypeScript и Swift (`engines/`), обе реализации обязаны давать одинаковый результат на тест‑векторах из `vectors/`.
3. **Правовые правила** — что движок обязан учитывать и о чём предупреждать (раздел 5 и `legal/ru-rules.md`).

---

## 1. Принципы

- **Хранится только введённое, вычисляемое не хранится.** Масса, доли, компенсация, цена иска, пошлина, подсудность, сроки — результат функций движка над документом. Единственное исключение — явные ручные переопределения (`*_override`) с пояснением.
- **Позиции сторон раздельно.** У каждого актива и долга есть позиция супруги и позиция супруга с обоснованием; расхождение — это «спор», который UI подсвечивает, а движок учитывает по выбранному в сценарии правилу.
- **Оценка — список, не число.** У объекта много оценок (стороны, оценщик, экспертиза, суд, кадастр, цена продажи, согласованная), каждая с датой и источником. Сценарий выбирает, какую применять.
- **Долги — не отрицательные активы.** Отдельная сущность с кредитором, остатком на дату, признаком «на нужды семьи» и доказательствами. Распределяются, а не «передаются».
- **Сценарии сохраняются.** Иск, встречный иск, проект мирового, вариант по экспертизе, решение суда — разные сценарии над одним реестром, сравниваются бок о бок.
- **Нейтральная модель, российский расчёт.** Сущности не привязаны к юрисдикции; расчётные режимы задаются полем `regime`. В v2 реализован только `ru_community_property`.
- **Никаких персональных данных в этом репозитории.** Векторы и примеры — синтетические или обезличенные.

## 2. Документ

Корень документа (`MaritalPropertyCase`):

| Поле | Назначение |
|---|---|
| `schema_version` | всегда `2` |
| `regime` | правовой режим расчёта, пока только `ru_community_property` |
| `meta` | служебное: когда и чем экспортирован, `source.system`, `source.case_guid`, `source.usn` (для оптимистической блокировки в Legalic) |
| `facts` | факты брака: даты регистрации / фактического прекращения отношений / расторжения, брачный договор, соглашение о разделе, стороны, представители, дети, срок давности |
| `assets[]` | реестр имущества |
| `liabilities[]` | реестр обязательств |
| `scenarios[]` | варианты раздела |
| `court_case` | судебное дело: суд, номер, судья, заседания, ходатайства, экспертизы, решение |
| `ui`, `extensions` | свободные объекты для приложений; движок игнорирует |

Полное описание полей — в схеме (описания `description` у полей — часть спецификации).

### 2.1. Хранение в Legalic

`context_json.marital_property` = весь документ. Поля `facts.children` и `facts.parties.*_person_guid` дублируют данные пространства `family`, если оно используется другими модулями дела; при расхождении источником истины для модуля раздела считается `marital_property`. Запись — `POST /backend/case/{guid}` с проверкой `usn`: если `meta.source.usn` устарел, сервер отвечает 409 и клиент делает merge.

### 2.2. Хранение в LawMatic Divorce

Файл `.divorce` = тот же документ + секция `ui` (настройки дашборда, зум таймлайна). Файлы без `schema_version: 2` приложение не открывает и объясняет почему. Экспорт «JSON v2» из приложения импортируется во вкладку Legalic без преобразований, и наоборот.

## 3. Идентификаторы и связи

- `Asset.id`, `Liability.id`, `Valuation.id`, `Scenario.id`, `Child.id` — строки, уникальные в пределах документа (рекомендуется UUID).
- `*_guid` — GUID сущностей Legalic (контакты, документы, суды). В автономном режиме могут быть `null`; тогда реквизиты берутся из локальных копий (`facts.persons`, `creditor_name`, `file_url`).
- `Liability.linked_asset_id` ↔ `Asset.encumbrance_liability_ids[]` — связь «ипотека ↔ квартира». Движок проверяет согласованность и предупреждает.
- `ScenarioAssetItem.valuation_id` должен ссылаться на оценку того же актива.

## 4. Движок

Все функции чистые и детерминированные. Деньги — в рублях; иностранная валюта конвертируется по `fx_rate` на `fx_date` до расчёта. Результаты — числа с копейками, без округления внутри цепочки; округление — только при выводе (см. 4.8).

### 4.1. `mass(case, scenario)` — состав массы

Для каждого `asset_items[i]` с `include = true`:

1. **Стоимость** `V` = `value(asset, item, scenario)` (4.2).
2. **Позиция** `P` = `item.accepted_position ?? резолвер по позициям сторон`:
   - обе стороны `common` → `common`;
   - обе `personal_wife` / `personal_husband` / `excluded` → объект вне массы;
   - иначе → `disputed`, применяется правило сценария: для `kind = claim` берётся позиция истца, для `counterclaim` — ответчика, для `court_decision`/`expert`/`settlement` `accepted_position` обязателен (иначе предупреждение `scenario.disputed_position_unresolved`).
3. **Доля личных вложений** `s` = `item.personal_share_override ?? claimed_personal_share выбранной позиции ?? расчёт из funding`: `(personal_wife + personal_husband) / (common + personal_wife + personal_husband + maternity_capital + loan)`; если `funding` пуст — `0`.
4. **Доля детей** `c` (маткапитал): `item`/`asset.children_share_override ?? maternity_capital / общая цена приобретения / число членов семьи × число детей` — по п. 13 Обзора ВС РФ от 22.06.2016 доли считаются от суммы маткапитала, а не от всей цены. Требует подтверждения формулы юристом на векторе `division/maternity-capital-*` (ещё не написан).
5. **Общая часть** `C = V × (1 − s − c)`, если `P ∈ {common, partly_personal}`; иначе `0`.
6. **Add‑back**: если `asset.disposed` заполнен и `item.add_back = true`, объект входит в массу общей частью `C` и считается полученным отчуждателем (`disposed.by`), независимо от `assigned_to` (п. 16 Пленума ВС № 15).
7. **Граница массы**: объекты с `acquired_at` позже `facts.separated_at` (или `dissolved_at` при `mass_cutoff = dissolution`) по умолчанию вне массы с предупреждением `asset.acquired_after_separation`; включение — только явным `include = true` + `accepted_position`.

Для каждого `liability_items[i]` с `include = true` и `treat_as_common = true`: общая сумма `L = outstanding.amount` (в рублях). Если `family_purpose.status ≠ proven` — предупреждение `liability.family_purpose_not_proven` (презумпции общности нет, п. 5 Обзора ВС № 1 (2016)).

Результат: `assets_common = ΣC`, `liabilities_common = ΣL`, `net = assets_common − liabilities_common`.

### 4.2. `value(asset, item, scenario)` — выбор оценки

1. Если задан `item.valuation_id` — эта оценка.
2. Иначе по `scenario.valuation_policy`:
   - `court_first`: `court` (с `accepted_by_court`) → `expert` → `appraiser` → `settlement` → `market_reference` → оценка стороны‑автора сценария → оценка другой стороны → `cadastral` → `sale_price`;
   - `wife` / `husband`: `party_wife` / `party_husband`, иначе как `court_first`;
   - `blended`: среднее `party_wife` и `party_husband`, если есть обе, иначе имеющаяся, иначе как `court_first`;
   - `per_item`: без `valuation_id` — предупреждение `asset.no_valuation_selected`, объект считается без стоимости (`unvalued`).
3. При нескольких оценках одного типа берётся с самой поздней `valued_at`.
4. Оценка старше 6 месяцев на дату расчёта — предупреждение `valuation.stale`.
5. Валюта ≠ RUB без `fx_rate` — ошибка `valuation.fx_missing`.

### 4.3. `divide(case, scenario)` — распределение

- `ideal.wife = net × wife_share`, `ideal.husband = net × (1 − wife_share)`.
- `received.assets[side]` = Σ общих частей `C` объектов с `assigned_to = side`; для `joint_shares` — по `share_ratio`; для add‑back — отчуждателю; `sale`, `court`, `children`, `null` → в `unallocated`.
- `received.liabilities[side]`: `allocation = proportional` → `L × доля стороны`; `wife`/`husband` → целиком стороне.
- `received.net[side] = received.assets[side] − received.liabilities[side]`.
- `compensation`: `diff = received.net.wife − ideal.wife`; если `diff > 0` — `from: wife, to: husband, amount: diff`; если `< 0` — наоборот; `0` — `from/to = null`. При `unallocated > 0` компенсация помечается предварительной (`warnings: division.unallocated_present`).
- Если `wife_share ≠ 0.5` и `deviation_grounds` пуст — предупреждение `scenario.deviation_without_grounds` (п. 2 ст. 39 СК РФ).
- Результат содержит `asset_lines[]` — построчная раскладка по объектам сценария: `asset_id`, выбранная стоимость (`value`, `null` если оценка не взята), общая часть (`common_part`), `assigned_to`, `in_mass`, `unvalued`. Таблица, иск и панель итога берут стоимость объекта из этой строки, а не из своей формулы. Swift-движок v2 раскладку не отдаёт; на паритет итоговых сумм это не влияет.

### 4.4. `claimPrice(case, scenario)` — цена иска (ст. 91 ГПК РФ)

Определяется для `plaintiff` из `scenario.claim`:

`claim_price = Σ стоимости объектов (общая часть), которые истец просит признать за собой (assigned_to = plaintiff) + требуемая истцом компенсация (если compensation.to = plaintiff)`.

Требует подтверждения юристом: включать ли в цену иска (а) объекты, уже оформленные на истца, если он просит «признать право»; (б) долю в общем долге, которую истец просит возложить на ответчика. По умолчанию (а) — включать, (б) — не включать; оба правила настраиваются флагами в будущей версии. `claim_price_override` заменяет расчёт с обязательным `claim_price_note`.

### 4.5. `courtFee(input)` — госпошлина

Вход — `CourtFeeInput` из `schema/vector.schema.json`. Шкала пп. 1 п. 1 ст. 333.19 НК РФ в редакции ФЗ от 08.08.2024 № 259‑ФЗ (для заявлений, поданных с 09.09.2024), физические лица:

| Цена иска, ₽ | Пошлина |
|---|---|
| до 100 000 | 4 000 |
| 100 001 – 300 000 | 4 000 + 3 % от суммы свыше 100 000 |
| 300 001 – 500 000 | 10 000 + 2,5 % свыше 300 000 |
| 500 001 – 1 000 000 | 15 000 + 2 % свыше 500 000 |
| 1 000 001 – 3 000 000 | 25 000 + 1 % свыше 1 000 000 |
| 3 000 001 – 8 000 000 | 45 000 + 0,7 % свыше 3 000 000 |
| 8 000 001 – 24 000 000 | 80 000 + 0,35 % свыше 8 000 000 |
| 24 000 001 – 50 000 000 | 136 000 + 0,3 % свыше 24 000 000 |
| 50 000 001 – 100 000 000 | 214 000 + 0,2 % свыше 50 000 000 |
| свыше 100 000 000 | 314 000 + 0,15 % свыше 100 000 000, но не более 900 000 |

Дополнительно:

- `prior_right_established = true` → вместо шкалы фиксированно 3 000 ₽ (пп. 3 п. 1 ст. 333.20 → пп. 3 п. 1 ст. 333.19);
- `divorce_claimed = true` → + 5 000 ₽ (пп. 5 п. 1 ст. 333.19; суммирование — п. 12 ст. 333.20);
- `injunction_requested = true` → + 10 000 ₽;
- `stage = appeal` → 3 000 ₽; `cassation` → 5 000 ₽; `supreme_court` → 7 000 ₽ (вместо шкалы);
- `plaintiff_type = organization` — отдельная шкала, в v2 не реализована (предупреждение);
- `filed_at` раньше 09.09.2024 — старая шкала, в v2 не реализована (ошибка `fee.scale_not_supported`).

Результат — сумма и `breakdown[]` по элементам с текстовым обоснованием. Округление до рубля (см. 4.8) требует подтверждения.

Не входит в расчёт пошлины, но считается отдельно (`extraCosts`): возврат 70/50/30 % при мировом соглашении по стадиям (п. 3 ст. 333.40 НК РФ); нотариальный тариф за соглашение о разделе — 0,5 % от суммы, минимум 300 ₽, максимум 20 000 ₽ (пп. 5 п. 1 ст. 333.24) плюс услуги правового и технического характера по региону; брачный договор — 500 ₽ плюс УПТХ.

### 4.6. `jurisdiction(claim_price)` — подсудность

`claim_price ≤ 50 000` → `magistrate` (мировой судья, п. 3 ч. 1 ст. 23 ГПК РФ), иначе `district`. Территориальная подсудность — только подсказка: по месту жительства ответчика (ст. 28), исключительная по недвижимости (ст. 30) — при оспаривании сделок / объектах незавершённого строительства; автоматически не выбирается.

### 4.7. `deadlines(case)` — сроки

| Срок | Правило | Код |
|---|---|---|
| Исковая давность по разделу | 3 года с `facts.limitation.violation_known_at` (п. 7 ст. 38 СК РФ, п. 19 Пленума № 15), не ранее `dissolved_at`; в браке не течёт; `override_deadline` заменяет | `deadline.limitation` |
| Оспаривание сделки без согласия | 1 год с даты, когда узнал (п. 3 ст. 35 СК РФ) — от `asset.disposed.at`, если иная дата не указана | `deadline.disposal_challenge` |
| Оспаривание брачного договора | 1 год с момента, когда узнал о крайне неблагоприятном положении (п. 2 ст. 44 СК РФ, ст. 181 ГК РФ) | `deadline.contract_challenge` |
| Апелляция | 1 месяц с `court_case.decision.final_form_at` (ст. 321 ГПК РФ) | `deadline.appeal` |
| Кассация | 3 месяца со вступления в силу (ст. 376.1 ГПК РФ) | `deadline.cassation` |

Уровни тревоги: `info` (> 90 дней), `warning` (≤ 90), `critical` (≤ 30), `expired`.

### 4.8. Округление и представление

Внутренние расчёты — без округления. При выводе: суммы — до копеек; пошлина — до рубля по правилам п. 6 ст. 52 НК РФ (менее 50 копеек отбрасывается, 50 и более — до полного рубля) — **требует подтверждения** применимости к пошлине, до этого векторы пошлины используют «круглые» суммы.

### 4.9. `warnings(case, scenario)` — предупреждения

Коды предупреждений — строки вида `область.событие`; полный перечень ведётся в `legal/ru-rules.md` (колонка «Код»). Минимальный набор для v2: `asset.no_position_other_side`, `asset.personal_without_ground`, `asset.disposed_without_evidence`, `asset.acquired_after_separation`, `asset.partly_personal_needs_tracing`, `asset.maternity_capital_children_share`, `valuation.stale`, `valuation.missing`, `liability.family_purpose_not_proven`, `liability.bank_consent_required`, `scenario.deviation_without_grounds`, `scenario.disputed_position_unresolved`, `claim.price_mismatch_override`, `deadline.*`, `agreement.not_notarized`, `business.charter_consent_required`.

### 4.10. `claimDocument(case, scenario)` — структура иска

Возвращает структуру документа (заголовок, стороны, обстоятельства, перечень имущества, правовой режим, предложение о разделе, расчёт компенсации, цену иска и пошлину, просительную часть, приложения по ст. 132 ГПК РФ), а не текст. Рендер в DOCX/PDF — на стороне приложений. Детали — в версии 2.1.

## 5. Правовые правила

Перечень правил с реквизитами норм и практики ВС РФ — `legal/ru-rules.md`. Каждое правило имеет идентификатор `RU-nn`, и векторы в `legal_basis` ссылаются на нормы; движок ссылается на коды предупреждений.

## 6. Тест‑векторы

- Один вектор — один файл `vectors/<категория>/<имя>.json`, `id` совпадает с путём.
- Формат — `schema/vector.schema.json`. Для `kind = division` поле `input.case` валидируется по схеме документа.
- `status: draft` — рассчитано вручную; `confirmed` — подтверждено юристом или официальным калькулятором. В релиз 2.0.0 входят только `confirmed`.
- Реализация обязана проходить все векторы с допуском 0,01 ₽ по денежным величинам.
- Векторы из реальных дел — только после обезличивания (без ФИО, адресов, кадастровых номеров, VIN, номеров дел).

Категории: `division`, `fee`, `claim_price`, `deadlines`, `jurisdiction`, `warnings`, `roundtrip` (экспорт → импорт → идентичный JSON).

## 7. Версионирование

- `schema_version` меняется только при несовместимых изменениях документа. Совместимые добавления (новые необязательные поля, новые значения перечислений) — минорные версии спецификации (`2.1`, `2.2`) при том же `schema_version: 2`.
- Реализации указывают поддерживаемую версию спецификации; неизвестные значения перечислений обрабатываются как `other` с предупреждением.
- Ставки пошлины и пороги подсудности датированы (`effective_from`); при изменении закона добавляется новая таблица, старая не удаляется.
